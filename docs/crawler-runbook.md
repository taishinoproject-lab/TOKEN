# 自動収集の手順書（週1回の定期実行用）

作成日: 2026-10-07（T-301〜T-303）
関連: [decisions.md](./decisions.md) D-006 / [data-model.md](./data-model.md) §7・§8・§12 / [venue-selection.md](./venue-selection.md)

この手順書は、週1回起動される Claude Code のセッションが、**この文書だけを読んで**展覧会データの更新案を作れるように書いている。
APIキーは使わない。ページの取得と引用の照合は決定的なスクリプトが行い、本文を読んでデータにするのはセッション自身（AI）が行う。

---

## 0. 守ること（最優先）

1. **推測で書かない。** 会期・展示期間・展示室・料金・出品物は、取得したページの本文に書かれていることだけをデータにする。分からない値は書かない（項目を省くか `null`）。
2. **すべての事実に、原文どおりの引用（`sources[].quote`）を付ける。** 引用は、スナップショット（`crawl/snapshots/`）の本文からそのまま写す。要約・言い換え・補完をしない。
3. **照合できない項目は採用しない。** `npm run crawl:verify` が通らない引用は、引用を直すか、その項目をデータから外して「要確認」に書く。
4. **IDを変えない。** 既存の展覧会の題名が変わっても、`id` はそのまま（URLになるため）。
5. **刀匠・刀剣を推測で結び付けない。** `smith_id` / `sword_id` は、既存のIDで、名前（または `aliases`）が本文の表記と一致し、国や流派も矛盾しない場合だけ付ける。迷ったら付けずに `label` だけにして、「要確認」に書く。結び付けてよい条件と、新しい刀・刀匠を追加してよい条件は §9 に従う（条件を満たさないものは作らない）。
6. **画像を扱わない。** チラシや作品の画像を保存・埋め込みしない。リンクだけ（D-003、D-007）。
7. **他社の作品とのコラボ企画は掲載しない**（D-009、D-012-4）。刀剣の展示情報に限る。
8. **型（`src/lib/schema.ts`）とデータ設計を変えない。** 必要だと思ったら「要確認」に書く。
9. **PR を作るか、どのブランチに push するかは、セッションの指示に従う。** 指示のない操作（他のブランチへの push、マージ）はしない。

## 1. 全体の流れ

```
npm ci
npm run crawl:fetch        # ① 巡回：本文を crawl/snapshots/ に保存し、変化を crawl/changes.json に出す
（AI が読む）              # ② 抽出：変化のあったページを読み、data/exhibitions.json を更新する
npm run crawl:verify       # ③ 照合：引用が本文に実在するかを確認する
npm run lint && npm test && npm run build   # ④ 通常の検査（データ検証は build に含まれる）
npm run crawl:report       # ⑤ 報告：crawl/report.md に追加・変更点と引用・元URLを書き出す
git add / commit / push    # ⑥ 人の確認へ
```

### 各ファイルの役割

| ファイル | 内容 | コミットするか |
|---|---|---|
| `crawl/targets.json` | 巡回先（館ID・URL・種類・メモ）、User-Agent、間隔、1館あたりの上限 | する |
| `crawl/snapshots/{館ID}/*.txt` | 取得したページの本文テキスト（引用の照合元） | する（翌週の比較と、PR の確認に使う） |
| `crawl/snapshots/manifest.json` | URL とスナップショットのファイルの対応、取得日、本文が変わった日 | する |
| `crawl/changes.json` | 今回の巡回の結果（新規・変化あり・変化なし・失敗・見送り、増えた行・消えた行） | する |
| `crawl/report.md` | PR の本文用の要約。自動生成部分と、手で書く「要確認」 | する |

## 2. 巡回（`npm run crawl:fetch`）

- 実行すると、`crawl/targets.json` のすべての巡回先を順に取得する。1館だけなら `npm run crawl:fetch -- --venue tnm`。
- 礼儀正しい巡回のための決まり（スクリプトが自動で守る）:
  - 館（オリジン）ごとに `robots.txt` を取得して従う。404 などは「robots.txt なし」としてすべて許可、5xx や通信エラーのときはその館を取得しない。`Crawl-delay` があればそれに従う。
  - リクエストの間隔は `request_interval_ms`（2秒）以上空ける。
  - User-Agent は `TOKEN-crawler/0.1 (+https://github.com/taishinoproject-lab/token)`。
  - 1館あたり `max_pages_per_venue`（8ページ）まで。
- 本文の抽出は決定的（同じページからは同じテキスト）。HTML のコメント、script / style、ルビの読み（rt）は除く。PDF は unpdf でテキストにする。JSON は「キー: 値」の行にする。
- 本文が変わったページだけ、スナップショットのファイルが書き換わる。
- 通信エラー・タイムアウト（30秒）・HTTP 5xx・429 のときは、10秒以上空けて1回だけやり直す。それでも失敗したページだけが `error` になり、他のページ・他の館の巡回は続く。
- 失敗（`error`）があると終了コードが 1 になるが、他のページの結果は保存されている。失敗したページは前回のスナップショットが残るので、そのまま続けてよい。失敗の内容は「要確認」に書く。

### 結果の読み方（`crawl/changes.json`）

- `summary`: 件数。`changed_venues`: 本文が新規・変化した館。
- `pages[].status`: `new`（初回）/ `changed` / `unchanged` / `error` / `skipped`（robots.txt で禁止、上限超え）。
- `pages[].added` / `removed`: 増えた行・消えた行（先頭200行まで）。**ここだけで判断せず、スナップショットの全文を読む。**

**全館が `unchanged` なら、②〜⑤は不要。** 「変化なし」とだけ報告して終わる（スナップショットのファイルは変わらないが、`manifest.json` の取得日と `changes.json` は更新されるので、指示があればコミットする）。

## 3. 抽出（AI が行う）

### 3.1 何を読むか

1. `crawl/changes.json` で `new` / `changed` のページを確かめる。
2. そのページのスナップショット（`crawl/snapshots/{館ID}/…txt`）を**全文**読む。
3. `data/exhibitions.json` の、その館（`venue_id`）の展覧会をすべて読む。刀剣・刀匠の参照のため、`data/swords.json` と `data/smiths.json` も読む。

### 3.2 登録するもの・しないもの

- 登録する: **刀剣が主題の展覧会・展示**（刀剣の企画展・特別展、刀剣室の展示替え、草薙館の月替わりの刀剣展、現代刀の展覧会など）。
- 登録しない: 刀剣が主題でない展示（屏風、能面、文書などのコーナー展）。他社の漫画・ゲームとのコラボ企画（同時開催でも、その部分は題名・出品リストに入れない）。体験講座・奉納行事などの催し。
- すでに会期が終わった展覧会は、新しく追加しない。既存の展覧会は、終わっていても削除しない（削除はオーナーが判断する）。

### 3.3 既存の展覧会を照合する

その館の既存の展覧会1件ごとに、本文と比べて次のどれかにする。

| 結果 | すること |
|---|---|
| 会期・題名などが本文と一致した | 根拠の引用を `sources` に足し、`verified_at` を今日に、`confidence` を `"confirmed"` にする |
| 本文と違っていた | 本文のとおりに直し、引用を足す。直した点を報告に書く（`crawl:report` が自動で一覧にする） |
| 本文に情報がない（まだ発表されていない、ページから消えた） | 値は変えない。`confidence` は `"unverified"` のまま（`confirmed` だったものを下げるかは「要確認」に書いて、オーナーに任せる） |

- `confirmed` にする展覧会では、**引用で裏付けられない出品物（`exhibits`）や値を残さない。** 旧データ由来で裏付けのない値は外し、外したものを「要確認」に書く。
- 題名は本文の表記に合わせる（「（仮題）」「(仮称)」も含める）。題名が変わっても `id` は変えない。

### 3.4 新しい展覧会を追加する

`data/exhibitions.json` の形式（data-model.md §7）に従う。

```json
{
  "id": "2026-atsuta-jingu-muramasa",
  "title": "村正",
  "venue_id": "atsuta-jingu",
  "room": "剣の宝庫 草薙館",
  "start_date": "2026-10-28",
  "end_date": "2026-11-23",
  "official_url": "https://www.atsutajingu.or.jp/houmotukan_kusanagi/schedule/index02.html",
  "periods": [],
  "exhibits": [],
  "sources": [
    {
      "url": "https://www.atsutajingu.or.jp/houmotukan_kusanagi/schedule/index02.html",
      "title": "熱田神宮 草薙館 年間スケジュール",
      "retrieved_at": "2026-10-07",
      "quote": "令和8年10月28日～11月23日 村正"
    }
  ],
  "verified_at": "2026-10-07",
  "confidence": "confirmed"
}
```

- `id`: `開始年-館ID-英字`（英小文字・数字・ハイフンのみ）。題名をローマ字にした短い語にする。既存と重複させない。
- 日付: 和暦（令和8年＝2026年、令和9年＝2027年）を西暦の `YYYY-MM-DD` に直す。年が省略された終了日（例: 「令和9年1月1日～1月25日」の「1月25日」）は、開始日と同じ年として読み、開始日より前の日付になる場合だけ翌年とする。
- `official_url`: その展覧会の公式ページ。個別ページがなければ、会期が載っている館のページ。
- `room`: 本文にある展示室名だけ。
- `admission`: 本文にある一般料金だけ（例: `"一般 1,200円"`）。展覧会ごとの料金が書かれていない場合は省く。
- `periods`: 前期・後期などの区分が本文にある場合だけ。展示期間が会期の外にはみ出さないこと。
- `exhibits[].label`: 出品目録の表記どおり（例: `"重文 太刀 古青江貞次"`）。行をまたぐ表は、指定・名称・作者を空白でつなぐ。`period_ids` は、作品ごとの展示期間が本文にある場合だけ。
- 刀剣・刀匠の参照は 0. の 5 のとおり。リンクしない行も `label` だけで登録してよい。
- 展覧会が中止・延期と書かれていれば `status` を付ける。

### 3.5 引用（`sources[].quote`）の書き方

- **スナップショットの本文から、連続した文字列をそのまま写す。** 改行は空白1つにしてよい（照合のときに、空白・改行・全角半角・波ダッシュの字形の違いは無視される）。漢字・かな・数字・記号の違いは無視されない（旧字体を新字体にしない）。
- 1つの引用で、**事実と、それがどの展覧会のことかの両方**が分かるようにする。例: 会期なら「令和8年12月5日（土曜日）～令和9年2月14日（日曜日） 冬季特別展「古備前―刀剣王国の黎明（仮題）」」のように、日付と展覧会名を含む範囲を引く。料金が展覧会ごとの節にある場合は、節の見出しから料金まで、または料金から次の節の見出しまでを引く。
- 空白を除いて6文字以上にする（短すぎる引用はエラーになる）。
- 出品物は1行（1作品）ごとに1つの引用を付ける（例: 「重文 太刀 1口 古青江貞次 鎌倉時代・13世紀」）。
- `url` は `crawl/targets.json` の URL と**完全に同じ文字列**にする（照合はこの URL でスナップショットを探す）。`retrieved_at` は今日の日付。`title` は出典の名前（例: 「備前長船刀剣博物館 年間展示予定(2026年度)」）。
- 旧データ由来の、引用のない出典（`"旧データ（src/data）に記載のURL。内容は今回未確認"` など）は、同じ URL に引用付きの出典を足した場合は外してよい。

## 4. 検証

次をすべて実行し、すべて成功させる。

```
npm run crawl:verify   # 引用の照合（照合できない引用が1件でもあれば失敗）
npm run lint
npm test
npm run build          # データ検証（scripts/validate-data.ts）を含む
```

- `crawl:verify` が失敗したら、表示された引用をスナップショットの本文と見比べて、写し間違いを直す。本文にない内容なら、その項目をデータから外す（「要確認」へ）。
- `build` のデータ検証のエラー（参照切れ、日付の前後、展示期間のはみ出しなど）は必ず直す。警告は増やさないようにする。

## 5. 報告（`crawl/report.md`）

1. `npm run crawl:report` を実行する。基準（既定は `origin/main`）と比べた、追加・変更・削除の一覧と、根拠の引用・元URLが、`crawl/report.md` の自動生成部分（`<!-- crawl:report:auto:start -->` 〜 `end`）に書き出される。基準は、PR の向き先（作業ブランチの分岐元）にする。`origin/main` 以外なら `npm run crawl:report -- --base origin/<ブランチ名>`（先に `git fetch origin <ブランチ名>` を実行する）。
2. 自動生成部分の外に、手で次を書く（再実行しても消えない）。
   - **要確認**: 照合できずに採用しなかった項目、外した旧データの値、刀匠・刀剣のリンクを迷ったもの、取得に失敗したページ、ページの構造が変わった館など。
   - 巡回先を追加・変更した場合は、その理由。
3. この報告を、そのまま PR の本文に使えるようにする。

## 6. コミットと push

- 変更するファイル: `data/exhibitions.json`、`crawl/`（snapshots・changes.json・report.md、必要なら targets.json）。**それ以外は変更しない。**
- コミットメッセージは日本語で、先頭に `data:` を付ける（例: `data: 自動収集 2026-10-14（熱田神宮・備前長船）`）。
- push 先はセッションの指示に従う（指示がなければ push せず、報告だけをする）。

## 7. 巡回先の管理（`crawl/targets.json`）

- 巡回先を足すときは、**必ず対象館の公式ドメイン（D-006 で許可された15館のドメイン）のページだけ**にする。まとめサイトや観光サイトは巡回先にしない（出典にもしない）。
- 足す前に、ページを1回取得して、本文に展覧会情報があること（JavaScript で描画していないこと）を確かめる。本文が空のページは `error` になる。
- `note` に、そのページに何が載っているか、注意点を書く。
- `expect_text` に、そのページの本文に必ずある短い文字列（ページの見出しなど）を書く。本文にこの文字列がなければ、別の言語の版やエラーページが返ったとみなして `error` にし、前回のスナップショットを残す。
- URL を変えると、スナップショットのファイル名も変わる（新しいページとして `new` になる）。データの `sources[].url` も同じ文字列に直す。
- 1館あたり8ページまで。会期が終わった展示の個別ページは外してよい。

## 8. GitHub Actions が作った PR を起点にする（T-304）

巡回（①）は、GitHub Actions（`.github/workflows/crawl.yml`）が**毎週月曜 08:47（日本時間）**に自動で実行する。手動でも実行できる（GitHub の **Actions** → **週1回の巡回** → **Run workflow**。ブランチは `main` を選ぶ）。

### 8.1 Actions が行うこと

1. `npm ci` → `npm run crawl:fetch` を実行する。
2. `npm run crawl:actions` で `crawl/changes.json` を読み、本文が `new` / `changed` のページがあるかを判定する。
3. **変化がなければ、何もせずに終わる**（ブランチもPRも作らない。結果は実行の概要に出る）。
4. 変化があれば、`crawl/snapshots/` と `crawl/changes.json` を `crawl/YYYY-MM-DD` ブランチにコミットして push し、`main` に向けた PR を作る（ラベル `crawl`）。同じ名前のブランチがすでにあれば、末尾に実行IDを付ける。
5. 取得に失敗したページがあれば、PR 本文・実行ログ・実行の概要に一覧で出し、最後にジョブを失敗（赤）にする（PR は作られる）。GitHub から失敗の通知が届くので、それで気づける。

### 8.2 PR を受け取ったら（AI のセッション）

1. PR のブランチを取得して切り替える。
   ```
   git fetch origin crawl/2026-10-12
   git switch crawl/2026-10-12
   npm ci
   ```
2. **`npm run crawl:fetch` は実行しない**（巡回は Actions が済ませている。スナップショットは PR のものを使う）。
3. PR 本文の「変化のあった館とページ」と `crawl/changes.json` を見て、3. 抽出 → 4. 検証 → 5. 報告 の手順を行う。`crawl:report` の基準は `origin/main`（既定）のままでよい。
4. `data/exhibitions.json` と `crawl/report.md` をコミットし、**同じブランチ（`crawl/YYYY-MM-DD`）に push する**。新しいブランチや新しい PR は作らない。
5. `crawl/report.md` の内容を、PR の本文に追記する（ツールで PR 本文を編集できない場合は、PR へのコメントとして書く）。
6. 本文の変化がデータに関係しないもの（展示室の他の分野の入れ替え、ページの飾りの変更など）だけだった場合は、データを変えずに、`crawl/report.md` に「データの変更なし」と理由を書いて push する。

### 8.3 注意

- Actions（`GITHUB_TOKEN`）が作った PR では、CI（`.github/workflows/ci.yml`）は自動で始まらないか、承認待ちになる。抽出の結果を push すると CI が実行される。データの変更なしでマージする場合も、マージ前に CI が通っていることを確かめる。
  - 出典: <https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/trigger-a-workflow>（"events triggered by the `GITHUB_TOKEN` will not create a new workflow run"）
- 前の週の巡回の PR がマージされていないと、次の週の巡回は `main` のスナップショットと比べるため、同じ変化がもう一度 PR になる。古い PR は、マージするか閉じてから次の週を迎える。
- GitHub Actions は米国などのサーバーから接続する。館によっては国外からの接続を拒む可能性がある。特定の館が毎週 `error` になる場合は、「要確認」に書いてオーナーに伝える。
- オーナーは、リポジトリの **Settings** → **Actions** → **General** → **Workflow permissions** で「**Allow GitHub Actions to create and approve pull requests**」を有効にしておく必要がある（無効だと PR の作成で失敗する）。

## 9. 刀の結び付けと追加の基準（2026-11-16 の実例つき）

毎週の巡回 PR を処理するセッションが、同じ基準で判断を続けるための決まり。**迷ったら付けない・作らない**が原則で、迷ったものは §9.7 の書式で「要確認」に挙げる。

### 9.1 出品物を刀（`sword_id`）に結び付けてよい条件

次の **A か B のどちらか**を満たし、かつ **C** を満たすときだけ結び付ける。

- **A. 号で特定できる。** 出品リストの本文に号（「名物 ○○」「号 ○○」）が書かれていて、`data/swords.json` の `go` または `aliases` と一致する。
- **B. 指定と所蔵で特定できる。** 本文に、国の指定（国宝・重要文化財）と所蔵者が書かれていて、その組み合わせに当てはまる刀が1口しかないことが**本文から**分かる（列品番号、寄贈の経緯、「○○蔵の国宝とは別」などの記載がある）。
- **C. 矛盾がない。** 種別（太刀・刀・短刀…）、銘、所蔵者、指定のうち、本文に書かれているものが、登録済みの値と食い違わない。1つでも食い違えば結び付けない。

結び付けるときは、その行の本文を `sources[].quote` に入れる（§3.5）。刀ごとの展示期間が本文にあれば `period_ids` を付ける（§9.4）。

### 9.2 結び付けてはいけない例

| 場合 | 理由 | 2026-11-16 の実例 |
|---|---|---|
| 銘だけ・刀匠名だけの行 | 同じ銘の刀が複数ある | 福岡市博物館「刀 行光」「刀 和泉守兼定」「脇差 銘 備州長船成光」、東京国立博物館「刀 堀川国広」 |
| 同じ銘・同じ年紀の刀が同じ展覧会に複数ある | 行を取り違える | 刀剣博物館 目録 No.38（重要文化財）と No.39（重要美術品）は、どちらも「津田越前守助広／延宝七年二月日」 |
| 個人蔵で、号がない | 所蔵で1口に絞れない | 刀剣博物館 目録 No.2「重要文化財 刀 銘 長曽祢興里入道乕徹 個人蔵（刀剣博物館寄託）」 |
| 指定と所蔵は分かるが、同じ表記の刀がその館にほかにないことを本文から確かめられない | 「1口しかない」が推測になる | 徳川美術館「重要文化財 刀 無銘 助真」「重要美術品 太刀 銘 近村」 |
| 号が同じでも、所蔵者が違う | 別の刀 | 永青文庫蔵の庖丁正宗（豊田市博物館に出品）と、徳川美術館蔵の庖丁正宗。「三日月宗近 影」（復元刀）と三日月宗近 |
| 同じ刀匠・同じ指定でも、本文が別の刀だと書いている | 別の刀 | 備前長船刀剣博物館の「重要文化財 太刀 銘 信房作」（寄贈品）と、致道博物館蔵の国宝「太刀 銘 信房作」（公式ページに「展示はございません」） |
| 展示期間が分からない | 展示していない刀が「いま会える刀」に出る | 豊田市博物館の庖丁正宗（前期）・古今伝授の太刀（後期）。前期・後期の日付が公式ページにない |
| 既存の刀と同じかもしれないが、本文に決め手がない | 推測になる | 福岡市博物館「重要美術品 刀 二字国俊」と、登録済みの `niji-kunitoshi-katana-1`（所蔵「不明」）。東京国立博物館の旧データ「大太刀 直次」と `aoe-otachi-1` |

刀匠（`smith_id`）も同じ考え方で、名前または `aliases` が本文の表記と一致し、国・流派が矛盾しないときだけ付ける。同名で代の違う刀工（兼定、助広、国広、行光など）は、本文に代や通称が書かれていなければ付けない。

### 9.3 新しい刀を追加する手順

追加してよいのは、§9.1 の A か B で**個体を1つに特定でき**、登録済みの刀のどれとも違うと分かるものだけ。

1. **どの出典から何を取るか。** 値ごとに、次の出典の本文から取る。巡回先（`crawl/targets.json`）のページなら `quote` を付ける。
   | 値 | 取る出典 |
   |---|---|
   | 号・指定・所蔵・種別 | 出品リスト（作品リスト）の、その刀の行 |
   | 銘・法量（刃長・反り）・時代・由来 | 所蔵館の公式ページ（解説、過去の展示のアーカイブ、蔵品の一覧）。出品リストに書かれていればそれ |
   | 展示期間 | 出品リストの備考、年間スケジュール、目録の前期・後期の欄 |
   - 所蔵館のページに銘がなければ、所蔵館のドメイン内でほかのページを探し、巡回先に足す（§9.6）。
   - 巡回の対象外のドメイン（ColBase、文化遺産オンライン、他館のサイトなど）で確かめた値は、`quote` を付けず、`title` に「何が書いてあったか」を書く。**その値は「根拠が弱い」として、PR の「要確認」に必ず挙げる。**
   - 記憶や一般に知られていること（「日本号は無銘」など）は、出典がなければ書かない。
2. **号・銘・作者を分ける。**（data-model.md §6）
   | 本文の表記 | `go` | `mei` / `mei_kind` | `attributions` |
   |---|---|---|---|
   | 国宝 刀（名物 観世正宗） 相州正宗 ＋ 別の出典で「無銘」 | 観世正宗 | 無銘 / 無銘 | masamune・極め（要確認に挙げた） |
   | 刀 名物「城井兼光」…無銘だが備前長船派の兼光の作という | 城井兼光 | 無銘 / 無銘 | osafune-kanemitsu・伝（「という」のため） |
   | 国宝 刀 名物「へし切長谷部」…「長谷部国重本阿（花押）」と「黒田筑前守」の金象嵌銘 | 圧切長谷部（別名に「へし切長谷部」） | 長谷部国重本阿（花押）／黒田筑前守 / 金象嵌銘 | hasebe-kunishige・極め（「鑑定した」のため） |
   | 重要文化財 刀 銘 住東叡山忍岡辺長曽祢虎入道／寛文拾一年二月吉祥日 | null | 本文のとおり / 銘 | nagasone-kotetsu・在銘 |
   - `mei` は本文の字のまま（旧字体を直さない。「乕」を「虎」にしない）。行をまたぐ銘は「／」でつなぐ。
   - 帰属の根拠: 本人の銘がある → 在銘 ／ 無銘で「極め」「鑑定」と書かれている → 極め ／ 「伝」「〜という」 → 伝。本文に根拠がなければ、いちばん弱い「伝」にするか、`attributions` を空にして要確認に挙げる。
   - 銘が出典にないときは `mei: "不明"` とする（画面には出ない）。号の読みが出典になければ `go_reading: null`。
   - `designation` は本文に書かれた国の指定。日本美術刀剣保存協会の認定（特別重要刀剣など）は `nbthk_rank` に入れる（D-012）。国の指定が書かれていないときに「未指定」とするのは、出品リストに指定の欄や凡例があって、その刀に記号がない場合だけ。それ以外は「不明」。
3. **ID を付ける。** 号があれば号のローマ字（`kanze-masamune`）。なければ `刀匠ID-種別-連番`（`nobufusa-tachi-2`）。一度付けたら変えない。
4. **刀匠が登録されていないとき。** 本文に名前・国・流派が書かれていれば、その記載を出典に、新しい刀匠として登録する（例: `osafune-kanemitsu`「兼光」＝「備前長船派の兼光」）。既存の刀匠と同一人物かどうかは推測しない。代が本文になければ `generation` を入れず、`description` にそのことを書く。
5. **出品物に `sword_id` を付け、`npm run build` の成果物で確かめる。** トップ「いま会える刀」に出る刀は、展示期間が今日を含むことを本文でもう一度確かめる。

**2026-11-16 に追加した8口**（判断の見本）

### 9.4 出品物の展示期間と、展覧会の会期が食い違うとき

**会期は会期のページの記載どおり、出品物の展示期間は `periods` と `period_ids` で、分けて記録する。** 会期を勝手に短くしない。

東京国立博物館の例（`2026-tnm-honkan-13-1027`）:

- 作品リスト: 「本館 3室 2026年10月27日（火） ～ 2027年1月24日（日）」 → `start_date` / `end_date` はこのとおり。
- 年間スケジュール: 観世正宗は 2026/10/27〜2026/12/13。料金のページ: 「2026年12月14日(月)～2027年4月25日(日)まで、本館2～3室は…閉室」。
- → `periods` に `{ "id": "12月13日まで", "start_date": "2026-10-27", "end_date": "2026-12-13" }` を作り、3室の出品物に `period_ids: ["12月13日まで"]` を付けた。根拠の引用を2つとも `sources` に入れた。
- 刀ごとの終了日が本文にあるのは観世正宗だけで、ほかの15口は閉室の記載からの読み取り。**読み取りで決めた部分は「要確認」に書く。**

前期・後期のある展覧会は、区分の日付が本文にあるときだけ `periods` を作る（日付がなければ、前期・後期の別は `note` に書くだけにして、`sword_id` は付けない）。目録の「○」がどの列にあるかが本文から分からないPDFは、PDFを画像にして目で確かめ、確かめたことを PR に書く。

### 9.5 終了した展覧会の引用

会期が終わると、公式ページから記載が消えて `crawl:verify` が失敗することがある。終了した展覧会のデータは削除しない（§3.2）。引用は次のように扱う。

| ページの種類 | すること | 例 |
|---|---|---|
| その展覧会だけの個別ページ・作品リスト | **巡回先（targets）から外し、会期中に取得したスナップショットと `manifest.json` の項目を残す。** 本文が変わってしまった場合は、`git checkout origin/main -- <ファイル>` で会期中の本文に戻し、`manifest.json` のその項目も元に戻す。`targets.json` の近くの `note` に、外した理由を書く | 佐野美術館「名刀のいろは」の展覧会ページ、東京国立博物館の前の会期の作品リスト（id=8466）、福岡市博物館 第Ⅰ期の出品リスト |
| 一覧ページ（開催中の展覧会、展覧会一覧） | ページに残っている表記（「過去の展覧会」の欄など）に引用を直す。残っていなければ、その出典の `quote` を外し、`title` に「（YYYY-MM-DD に取得。会期の終了後は記載がない）」と書く。別のページ（年間スケジュール）の引用が残っていれば、それで足りる | 徳川美術館「ときめく箱」、刀剣博物館「鈴木嘉定コレクション寄贈品展」 |

どちらも、終了した展覧会の値（会期・出品物）は変えない。

### 9.6 出品リストのページが巡回先に入っていないとき

1. 開催中・開催予定の展覧会ごとに、作品リスト（HTML または PDF）へのリンクを、スナップショットの本文と公式ページで探す。東京国立博物館は、展示室一覧の「展示作品リストへ」（`controller=item&id=…`）。
2. **対象館（14館）の公式ドメインのページだけ**を `crawl/targets.json` に足す（§7）。`expect_text` と `note` を書く。1館8ページまで。上限を超えるときは、終了した会期のページを外す（§9.5）。
3. `npm run crawl:fetch -- --venue <館ID>` でその館だけ取得する。**実行すると `crawl/changes.json` がその館の結果だけに上書きされる**ので、実行前に退避し、実行後に元へ戻して、新しいページの項目（`status: "new"`）を足す。
4. PDF は、取り出した本文を読んで使えるか確かめる。行と値の対応が本文から決まらないPDF（刀剣博物館の目録）は、対応を目で確かめたものだけを使う。文字が1字ずつに分かれるPDFは使わない。
5. 対象外のドメイン、robots.txt で禁止、取得の失敗（熱田神宮の 503 など）は、追加せずに「要確認」に挙げる。回避しない（D-021）。「いつから確認できていないか」を必ず書く。

### 9.7 「要確認」の書式

PR の本文（`crawl/report.md` の手書きの部分）に、1件ずつ次の形で書く。オーナーが「はい／いいえ」か、選択肢の1つで答えられる形にする。

```
N. **［館名］対象（ID や出品物の表記）** — 何を迷ったか。
   - 本文: 「（原文の引用）」 — URL
   - いまのデータ: （変えていない／仮にこうした）
   - 選択肢: (1) … (2) …　／　必要なもの: （取得できていないページやドメイン）
```

書く対象:

- 結び付けを見送った出品物と、その理由（§9.2 のどれか）
- 本文からの読み取りで決めた値（「未指定」、帰属の根拠、展示期間など）と、対象外のドメインで確かめた値
- 外した値・外した展覧会、`confirmed` から下げるか迷ったもの
- 取得できなかったページ・館（いつから確認できていないか）

## 10. 毎週の巡回 PR を処理する依頼文（ひな形）

GitHub Actions が作った巡回の PR（`crawl/YYYY-MM-DD`）を、Claude Code（Opus）のセッションに渡すときの文面。`［ ］` の中を書き換えて使う。

```
巡回の PR #［番号］（ブランチ crawl/［YYYY-MM-DD］）を処理してください。
CLAUDE.md、docs/decisions.md、docs/data-model.md、docs/crawler-runbook.md を読んでから始めてください。

【すること】
1. docs/crawler-runbook.md の §8.2 の手順で、変化のあったページを読み、data/exhibitions.json を更新する。
   npm run crawl:fetch は実行しない（スナップショットは PR のものを使う）。
   ただし、開催中・開催予定の展覧会の作品リストが巡回先に入っていない場合は、§9.6 の手順で追加して、その館だけ取得する。
2. 出品物と刀の結び付け、新しい刀の追加は、§9 の基準に従う。
   - 号、または指定と所蔵で、個体を1つに特定できるものだけ。迷ったら付けない・作らない。
   - 刀匠は推測で統合しない。
   - 展示期間が本文にない刀は、結び付けない。
3. 会期が終わった展覧会は削除しない。引用が照合できなくなったものは §9.5 のとおりに扱う。
4. 他社の作品とのコラボ企画に関わる記述は掲載しない（D-009、D-012-4）。
5. npm run crawl:verify、npm run lint、npm test、npm run build をすべて通す。
6. npm run build の成果物（dist/index.html）で、トップ「いま会える刀」に、今日の時点で展示中の刀だけが出ていることを確かめる。
7. npm run crawl:report を実行し、crawl/report.md の手書きの部分に、変更点と「要確認」（§9.7 の書式）を書く。

【守ること】
- 館ごとにコミットする。同じブランチ（crawl/［YYYY-MM-DD］）に push する。新しい PR は作らない。マージはしない。

【最後に報告すること】
- 変更点（館ごと）、追加・結び付けた刀と、その引用・元ページの URL
- 「要確認」の一覧（私が答える必要のあるもの）
- 確認できなかった館と、いつから確認できていないか
- 前の週までの巡回の PR で、閉じてよいもの

［今週だけの指示があれば、ここに書く。例: ○○館の展覧会 △△ は、公式ページで確認できなければ外す］
```
